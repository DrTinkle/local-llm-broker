# Client integration

The broker exposes native job endpoints at `http://127.0.0.1:1235` and a bounded OpenAI-compatible Chat Completions subset at `http://127.0.0.1:1235/v1`. All routes except `/health` require the locally generated bearer token.

Shell-capable agent sessions should use the `llm-broker` CLI and retain the returned job ID. A generic OpenAI client can set its base URL to `http://127.0.0.1:1235/v1`, supply the bearer token, select one of your profiles (`llm-broker profiles` lists them; the `/v1/models` endpoint returns the same names), and send `messages` with `n=1` and bounded generation parameters. A profile marked as not thinking answers without a reasoning phase. The LM Studio model ID also works as the `model` value; when a thinking profile and a non-thinking twin share that model, the ID means the thinking profile, so use the twin's name for a non-thinking answer. On profiles with `supports_vision = true` (the `vision` column of `llm-broker profiles`), a message can include images as `image_url` parts that carry an inline base64 data URL. Other profiles reject images. The `llm-broker` CLI sends text only.

Supported compatibility fields include text and image `messages` (images only on vision profiles), configured `model`, `n=1`, `stream`, bounded output, common sampling parameters, tools/tool calls as pass-through data, and structured-output options supported by the installed backend. The broker does not execute tools. Unsupported fields and input other than text or inline images are rejected rather than dropped. Remote image URLs are rejected; the broker never fetches them. Request bodies are limited to 10 MiB. The broker estimates prompt tokens at submit (fitted per character class) to choose a tier, then counts the text exactly with the loaded model's tokenizer before the job runs; each image counts as its pixels / 1,024 + 2 tokens, read from the image's header (4,096 if the header cannot be read). An optional, broker-specific `tier` field (`low`, `medium`, `high`, or `auto`) selects the load tier; clients that cannot add fields can append it to the model name instead, as in `<profile>:high`. Without a tier, the broker picks the smallest one the request fits. Responses, Anthropic Messages, embeddings, audio input, and MCP are not claimed as supported.

To watch the broker (a dashboard, a status pill), subscribe to `GET /status/stream`, a server-sent event stream with a `status_snapshot` on connect and on each change and a `: keep-alive` comment every 30 seconds, instead of polling `/status`. One server-side subscription can feed any number of browser tabs. See "Watching status without polling" in [operations](./operations.md).

Native job submissions include `client_id`, `project`, `task_label`, `profile`, `messages`, `generation`, an optional queue deadline, and an optional `tier`. Metadata is short and generic; do not put prompt or file contents in those labels. Idempotency keys are scoped to client ID for 24 hours.
